DeepSeek dsh-superagent
Super-agent 研究原型

一句话：一个面向单个 GitHub 仓库的主动式 Coding Agent。它不等人逐条下指令，而是常驻在线、并行推进多项工作，最后回到原对话交付，比如提交一个 Pull Request。

官方仓库：deepseek-ai/dsh-superagent-prototype

先说清楚定位：这不是正式产品。官方 README 原话是“Research prototype for reference only, not an official DeepSeek product”，并提醒：代码可能仍有 bug、工程风格可能不一致、与内部版本不完全相同、设计文章里的部分想法尚未实现。把它当成架构探索和研究代码，而不是开箱即用的生产工具。

它想解决什么问题

DeepSeek 的判断不是“模型还不够强”，而是人的注意力成了瓶颈。一个人同时盯三到五个 Agent 会话就已经吃力，任务越多，上下文同步、进度跟踪、结果检查的负担越重。Super-agent 的做法是把“会话管理”本身交给系统：人不用逐个会话去调度，系统负责分派、同步和交付，人只在真正需要决策或结果可用时介入。

官方给出的工作原则是：尽量少占用人的注意力，尽量多给价值。它只在被要求、或团队写好的规则允许时行动；也只在有人必须行动、或结果可用时才说话。

它是怎么工作的

  1. 监听：监听一个 GitHub 仓库，也可以选择接入飞书群聊。
  2. 接活：被授权的人提出需求，或者团队预先写好的规则命中，系统就开一个工单（Ticket）。
  3. 并行干活：每个工单在自己独立的 Agent 会话和目录里执行，互不干扰，可以多项任务并行。
  4. 回原处交付：做完后回到原来的对话交付，例如提交一个 Pull Request；Web 面板会集中显示需要人工决策的事项。

Router 与 Worker 两层

  • Router（常驻）：负责收消息、分派任务、保持全局连续性，相当于“总调度”。
  • Worker（隔离并行）：每个任务一个独立会话，负责真正写代码、跑检查，上下文相互隔离。

这种拆分的好处是：多任务并行时，人不用在多个会话之间来回切换、自己拼上下文；风险是：权限、凭证和每一份 PR 都必须经过人的检查，不能把整个仓库无条件交给它。

初步实验数字：怎么读才不被带偏

团队公布的初步实验是在模拟条件下做的：约 300 条模拟消息、约 20 项工作请求。结果如下：

12.4 分钟
Super-agent 任务完成时间 p50
15.7 分钟
Super-agent 任务完成时间 p95
29.5 分钟
单会话 + Subagent 对照组 p95（中性提示）

正确读法：这是一组团队自报的初步实验，不是独立基准，也没有测量真实代码质量。模拟消息和模拟工具的结果，不能直接等同于真实团队、真实代码库里的效果。看这组数字的意义在于“并行分派可能缩短等待时间”，而不是“它已经比所有现有工具更强”。

适合怎么用，不适合怎么用

适合先这样试点

  • 在沙箱或非关键仓库里跑，人工逐份审 PR 再合并。
  • 先从“被明确要求才动手”的模式开始，规则写清楚再放宽。
  • 按官方仓库的 SETUP.md 一步步部署，官方也建议让 Coding Agent 按 SETUP.md 带着做，因为步骤不少。

不建议直接这样用

  • 直接部署到生产仓库、给它宽泛权限、且不审 PR 就合并。
  • 把它当成 DeepSeek 正式产品或现成服务来采购、承诺交付。
  • 只看“能自己开 PR”就忽略它的原型警告：bug、与内部版本差异、未实现的设计都写在 README 里。
